# Task 6: restart-aware change notification

The core `ChangeWaiter` uses a bounded, versioned opaque cursor containing only Bog ID, worker generation, and sequence. A different Bog/generation or a sequence regression produces `reset: true`; any differing cursor produces `changed: true`. This is a notification API, not a retained event feed or replay guarantee. Clients should fetch their desired view after a change/reset.

Waits probe the tiny total view every 250 ms, with a maximum requested wait of 25 seconds. Timeout returns the latest successfully sampled cursor (up to 250 ms old); a slow worker may instead produce an unavailable error. Initial worker startup/read has a separate 25-second ceiling and can exceed a shorter requested timeout. No worker lease is held while sleeping, so maintenance may stop/restart a worker; frequent successful probes count as worker activity. Global waits are limited to 64 and per-Bog waits to 8, with RAII release on completion or cancellation. Authorization is rechecked before reads, after reads and before returning. The existing authorization implementation checks current app token expiry/revocation and workspace membership. OAuth principal expiry must be handled by the gateway.

The generation is sampled under the same worker lease as the sequence. The helper `cursor_for_response` is intended to attach a cursor to an existing view response while the caller still holds its lease; it must not combine a view response from an old worker with a later generation.

Verification passed: focused cursor/capacity unit test and actual-worker integration test covering wake, timeout, restart reset, revocation, capacity and cancellation. `cargo test -p bog-cloud --lib changes::tests` and `cargo test -p bog-cloud --test changes`. The integration test required escalation because sandboxed local socket creation prevents worker readiness. Worker binary was built with `cargo build -p bog-cloud-records --bin bog-records-worker`.
